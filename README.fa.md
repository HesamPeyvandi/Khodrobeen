# خودروبین (Khodrobeen)

> Looking for the English README? See [README.md](README.md).

سیستمی که به‌صورت خودکار آگهی‌های خودرو/وانت دیوار را در شهرهای انتخابی هر
کاربر رصد می‌کند، قیمت هر آگهی جدید را با تخمین «همراه مکانیک» مقایسه می‌کند،
و اگر قیمت دیوار پایین‌تر از تخمین بود، لینک آگهی را از طریق ربات تلگرام
برای کاربر ارسال می‌کند.

## معماری

```
                        ┌────────────────────┐
                        │   APScheduler       │   هر چند دقیقه یک‌بار
                        │  (run_scan_cycle)    │──────────────┐
                        └────────────────────┘               │
                                   │                          ▼
                     ┌─────────────┴───────────┐   ┌────────────────────┐
                     │   Divar Scraper           │   │ Hamrah Mechanic     │
                     │  (Playwright, app/services/│   │ Estimator           │
                     │   divar_client.py)         │──▶│ (app/services/       │
                     └─────────────┬───────────┘   │  price_estimator.py) │
                                   │                └──────────┬─────────┘
                                   ▼                           │
                        ┌────────────────────┐                │
                        │   deal_checker.py    │◀──────────────┘
                        │  (compare & persist)  │
                        └──────────┬───────────┘
                                   ▼
                        ┌────────────────────┐        ┌──────────────────┐
                        │  SQLite / SQLAlchemy │        │   Telegram Bot    │
                        │  (app/db)             │        │  (aiogram, app/bot)│
                        └──────────┬───────────┘        └────────┬─────────┘
                                   │                              ▲
                                   ▼                              │
                        ┌────────────────────┐                    │
                        │   Flask Admin Panel   │────notify deal──┘
                        │  (app/web)             │
                        └────────────────────┘
```

همه‌ی این‌ها در یک پروسه (`main.py`) اجرا می‌شوند: پنل وب روی یک ترد جدا،
بات و زمان‌بند روی event loop اصلی asyncio.

## ویژگی‌ها

- انتخاب شهرهای موردنظر از داخل ربات تلگرام (کیبورد این‌لاین)
- بررسی خودکار آگهی‌های تازه‌ی خودرو و وانت دیوار در آن شهرها
- تخمین قیمت هر آگهی با فرم «همراه مکانیک» و مقایسه‌ی خودکار
- ارسال آگهی‌های ارزان‌تر از تخمین به‌صورت خودکار در تلگرام
- پنل مدیریت وب (فارسی، راست‌به‌چپ) برای دیدن آمار و فعال/غیرفعال‌سازی کاربران
- ساختار اشتراک قابل توسعه: همین امروز فعال‌سازی دستی، بعداً اتصال درگاه واقعی
  فقط با اضافه کردن یک کلاس تازه در `app/services/payment/`

## عیب‌یابی: خطای اتصال به تلگرام هنگام اجرای محلی

اگه موقع اجرای `python main.py` این خطا رو دیدید:

```
aiogram.exceptions.TelegramNetworkError: ... Cannot connect to host api.telegram.org
```

این یک باگ کد نیست - یعنی از سیستم شما به سرورهای تلگرام دسترسی نیست (تلگرام
در ایران فیلتر است). دو راه‌حل:

1. **روی سروری خارج از ایران دیپلوی کنید** (مثلاً Render، طبق راهنمای بالا) -
   از اونجا این مشکل اصلاً پیش نمی‌آد چون سرور مستقیم به تلگرام دسترسی داره.
2. **برای تست محلی**، یا VPN سیستمی‌تون رو روشن کنید، یا آدرس پراکسی محلی‌تون
   رو در `.env` بدید:
   ```
   TELEGRAM_PROXY_URL=http://127.0.0.1:2080
   ```
   (هم `http://` و هم `socks5://` پشتیبانی می‌شه - آدرس و پورت دقیق رو از
   تنظیمات کلاینت VPN/فیلترشکن خودتون بگیرید). وقتی این مقدار خالی باشه
   (پیش‌فرض)، برنامه بدون هیچ پراکسی‌ای مستقیم وصل می‌شه - دقیقاً همون چیزی
   که روی سرورهای خارج از ایران لازم است.

## عیب‌یابی: تایم‌اوت مکرر صفحات جزئیات آگهی

اگه `list_new_listings` آگهی‌ها رو پیدا می‌کنه ولی `get_listing_detail` مدام
خطای `TimeoutError: Page.goto: Timeout ... exceeded` می‌ده (خودِ navigation
تایم‌اوت می‌کنه)، معمولاً یعنی مسیر شبکه به دیوار کند یا محدود شده - به
توضیح مسیر شبکه پایین‌تر مراجعه کنید. ولی اگه خطا `Locator.inner_text:
Timeout ... exceeded` باشه (navigation موفقه، ولی خوندن یه عنصر خاص گیر
می‌کنه)، مشکل چیز دیگه‌ایه: یه سلکتور داره چیزی رو پیدا می‌کنه که هیچ‌وقت
visible/stable نمی‌شه. این دقیقاً علت اصلی اکثر خطاهای واقعی بود که موقع
ساخت این پروژه دیدیم - یه سلکتور حدسی برای قیمت (`:text('تومان')`) داشت یه
عنصری رو پیدا می‌کرد که رو تقریباً هر آگهی، کل ۳۰ ثانیه‌ی timeout پیش‌فرض
رو معطل می‌موند. راه‌حل این بود که دیگه قیمت رو با یه کوئری جدا از DOM
نگیریم، بلکه از همون اسکن مطمئن ردیف‌های برچسب/مقدار که برای بقیه‌ی
مشخصات هم استفاده می‌شه بخونیمش (نگاه کنید به `SPEC_LABELS["price"]` تو
`divar_client.py`) - چون هم `list_new_listings` هم ردیف‌های برچسب/مقدار از
قبل timeout کوتاه و try/except دارن (۲ تا ۳ ثانیه روی هر آیتم)، پس یه ردیف
خراب دیگه کل صفحه رو برای ۳۰ ثانیه قفل نمی‌کنه.

### مودال کادر انتخاب خودرو قبلاً هیچ‌وقت بسته نمی‌شد

کادر انتخاب برند/مدل/سال/تیپ تو همراه مکانیک داخل یه مودال باز می‌شه. یه
مدتی، هیچی صریحاً بعد از انتخاب تیپ اون رو نمی‌بست - رو فیلدهای کارکرد/
وضعیت بدنه/رنگ پایینش می‌موند و به‌طور خاموش جلوی کلیک روی **همه‌شون** رو
هم‌زمان می‌گرفت (این ریشه‌ی واقعی اکثر خطاهای «not clickable» بود، نه یه
مشکل سلکتور تک‌تک فیلدها). تابع `_close_car_picker_modal()` تو
`price_estimator.py` حالا بعد از انتخاب تیپ می‌بندتش (دکمه‌ی تایید ← Escape
← کلیک بیرون از مودال، به همین ترتیب)، و `_dismiss_overlays()` هم بعد از
لود صفحه پاپ‌آپ‌های رایج کوکی/تبلیغ رو می‌بنده.

اگه بعد از این هم کلیک‌ها شکست خوردن، `DEBUG_SCREENSHOT_ON_CLICK_FAILURE=true`
رو تو `.env` بذارید - هر کلیک شکست‌خورده یه اسکرین‌شات کامل از صفحه تو
`./debug_screenshots/` ذخیره می‌کنه، سریع‌ترین راه برای دیدن اینکه دقیقاً
چی رو صفحه رو پوشونده، بدون نیاز به یه سشن مرورگر زنده.

اگه `list_new_listings` آگهی‌ها رو پیدا می‌کنه ولی `get_listing_detail` مدام
خطای `TimeoutError: Page.goto: Timeout ... exceeded` می‌ده، معمولاً یعنی
مسیر شبکه به دیوار از جایی که هاست کردید کند یا محدود شده. سایت‌های ایرانی
اغلب پشت یه لایه‌ی CDN/ضد-ربات (آرون‌کلود خیلی رایجه) هستن که ترافیکی که
شبیه ربات باشه رو کند می‌کنن یا drop می‌کنن - و «بازدید ده‌ها صفحه‌ی جزئیات
پشت‌سرهم از یک IP غیرایرانی» دقیقاً همین الگوئه. سه تنظیم تو `.env` این رو
حل می‌کنن، به ترتیب احتمال موثر بودن:

1. `SCRAPER_PROXY_URL` - ترافیک مرورگر خودِ اسکرپر رو از یه پراکسی با مسیر
   خوب به ایران رد می‌کنه. این مشکل شبکه رو واقعاً حل می‌کنه، نه فقط بیشتر
   صبر کردن روی یه اتصال محدودشده - اگه (۲) و (۳) کمک نکردن، اول این رو
   امتحان کنید.
2. `PAGE_TIMEOUT_MS` - اگه صفحات لود می‌شن ولی فقط کند هستن، این رو زیاد
   کنید (مثلاً `90000`).
3. `PAGE_GOTO_RETRIES` - هر لود صفحه از قبل با این تعداد retry (با backoff)
   تلاش می‌شه؛ زیاد کردنش پایداری رو به قیمت کندی بیشتر می‌خره.

اگه اسکن‌ها مدام کندتر از `POLL_INTERVAL_SECONDS` باشن، تو لاگ پیام
`maximum number of running instances reached` می‌بینید - این یعنی مکانیزم
جلوگیری از تداخل اسکن‌ها داره درست کار می‌کنه (باگ نیست)، ولی نشون می‌ده
اسکن‌ها عقب افتادن. حل مشکل تایم‌اوت بالا معمولاً این رو هم حل می‌کنه؛
به‌عنوان راه‌حل موقت هم می‌تونید `POLL_INTERVAL_SECONDS` رو زیاد و
`MAX_LISTINGS_PER_SCAN` رو کم کنید.

## دیپلوی روی Render (پلن رایگان)

فایل `render.yaml` آماده است. مراحل:

1. ریپو را به گیت‌هاب پوش کنید و در Render یک "Blueprint" جدید از روی آن بسازید.
2. متغیرهای محیطی با `sync: false` (توکن بات، شناسه ادمین، هش رمز عبور) را
   در پنل Render دستی وارد کنید.
3. بعد از دیپلوی موفق، آدرس سرویس را بردارید و در
   [UptimeRobot](https://uptimerobot.com) یک مانیتور HTTP روی
   `https://<your-app>.onrender.com/health` با فاصله‌ی هر ۵ دقیقه بسازید تا
   سرویس رایگان Render نخوابد.

### ⚠️ محدودیت مهم پلن رایگان Render: راه‌اندازی دیتابیس رایگان Postgres (Neon)

پلن رایگان Render دیسک پایدار (persistent disk) ندارد؛ یعنی فایل SQLite با
هر ری‌استارت/دیپلوی جدید پاک می‌شود و لیست کاربران و شهرهای انتخابی‌شون از
اول شروع می‌شود. پکیج `psycopg2-binary` از قبل تو `requirements.txt` هست،
پس تغییر به Postgres فقط یه تغییر `DATABASE_URL`ه:

۱. به [neon.tech](https://neon.tech) برید و یه اکانت رایگان بسازید.
۲. یه پروژه‌ی جدید بسازید (اسم/ریجن فرقی نداره - اگه گزینه داشت، ریجن نزدیک
   به سرویس Render رو انتخاب کنید).
۳. تو داشبورد پروژه، **connection string** رو پیدا کنید - چیزی شبیه این:
   `postgresql://user:password@ep-xxx.region.aws.neon.tech/dbname?sslmode=require`
   کاملش رو کپی کنید.
۴. تو Render، سرویستون رو باز کنید → **Environment** → مقدار `DATABASE_URL`
   رو ویرایش کنید → همون connection string رو جایگزین کنید → ذخیره. Render
   خودش دوباره دیپلوی می‌کنه.
۵. همین! نیازی به تغییر کد یا اسکیمای دیتابیس نیست - `init_db()` خودش
   تمام جدول‌ها رو موقع اولین اجرا روی دیتابیس جدید می‌سازه.

پلن رایگان Neon بعد از یه مدت بی‌فعالیتی دیتابیس رو خودش suspend می‌کنه و
با اولین اتصال بعدی دوباره بیدارش می‌کنه (این پروژه از قبل `pool_pre_ping=True`
تنظیم کرده تا این اتصال‌های قدیمی/خوابیده رو به‌جای خطا دادن، خودکار دوباره
وصل کنه) - تنها اثر قابل مشاهده‌اش اینه که اولین کوئری بعد از یه دوره‌ی
سکوت، کمی کندتر از حد معمول جواب می‌ده.

### ⚠️ منابع محدود پلن رایگان و Playwright

اجرای مرورگر Headless (برای اسکرپینگ دیوار و پر کردن فرم همراه مکانیک) به
RAM بیشتری نسبت به یک سرویس وب معمولی نیاز دارد. پلن رایگان Render (512MB)
ممکن است برای این کار کند یا ناپایدار باشد - این ریسکی است که در ابتدای
پروژه با هم روی آن توافق کردیم. اگر با خطاهای حافظه یا timeout مواجه شدید:

- `MAX_LISTINGS_PER_SCAN` و `POLL_INTERVAL_SECONDS` را در `.env` بزرگ‌تر کنید
  تا فشار کمتری بیاید.
- یا فقط بخش اسکرپینگ/زمان‌بند را روی یک VPS ارزان اجرا کنید و پنل/بات را
  همان‌جا نگه دارید (کد به همین شکل قابل تفکیک نوشته شده - `app/services` و
  `app/scheduler` هیچ وابستگی‌ای به Flask ندارند).

## جدول مپینگ برند/مدل

تطبیق متن آزاد با کادر جستجوی همراه مکانیک قابل‌اعتماد نیست، چون دیوار و
همراه مکانیک اغلب یه ماشین رو با اسم متفاوت صدا می‌زنن. `app/services/car_mapping.py`
یه جدول مپینگ دستی-بررسی‌شده (`app/data/car_brand_mapping.json`، حدود ۹۳۳
ردیف) رو در بر می‌گیره که اسم **دقیق** برند/مدل همراه مکانیک رو برای هر
آگهی دیوار می‌ده، به‌جای حدس زدن، هر وقت یه تطبیق پیدا بشه:

- اول ردیف‌های «تطبیق یافت شد» (۴۳۲ ردیف) امتحان می‌شن.
- اگه هیچی با اطمینان تطبیق نداشت، ردیف‌های «نیاز به بررسی» (۳۳۳ ردیف) به‌عنوان
  fallback استفاده می‌شن - بازم خیلی بهتر از حدس زدن آزاد.
- اگه هیچ‌کدوم نبود، `deal_checker.py` به همون heuristic قدیمی
  (`_split_brand_model` + `DOMESTIC_MODEL_TO_BRAND`) برمی‌گرده.

برای گسترش پوشش، جدول رو ویرایش کنید و دوباره به `app/data/car_brand_mapping.json`
export کنید (همون فرمت ردیف‌های موجود). `explore_hamrah_catalog.py` یه
اسکریپت کوچیک تعاملیه برای بررسی مسیر برند ← مدل تو کادر انتخاب خودرو، اگه
خواستید ردیف‌های جدید رو دستی تایید کنید.

## دیباگ کردن اسکرپرها به‌صورت لوکال

هم دیوار و هم همراه مکانیک اپ‌های React/Next.js هستن که ساختارشون به‌مرور
تغییر می‌کنه، پس عیب‌یابی اسکرپینگ خیلی راحت‌تر با **دیدن مرورگر واقعی**
انجام می‌شه تا خوندن لاگ سرور. سه تا اسکریپت برای این کار هست (از روت
پروژه، با venv فعال اجرا کنید):

- **`python local_test_watch.py [city_slug] [category_slug]`** — کل
  مسیر واقعی (گرفتن یه آگهی تازه ← استخراج مشخصاتش ← پر کردن فرم همراه
  مکانیک ← چاپ تخمین) رو تو یه پنجره‌ی مرورگر قابل‌مشاهده اجرا می‌کنه،
  بدون دست زدن به دیتابیس یا تلگرام. اولین چیزیه که باید بعد از هر تغییر
  سلکتور اجرا کنید.
- **`python debug_divar_specs.py <listing_url>`** — یه آگهی دیوار رو باز
  می‌کنه و کلاس/متن هر عنصر کاندید برای ردیف مشخصات رو چاپ می‌کنه، برای
  پیدا کردن سلکتور درست وقتی استخراج تو `divar_client.py` از کار افتاد.
- **`python debug_hamrah_picker.py "<query>"`** — کادر انتخاب خودروی
  همراه مکانیک رو باز می‌کنه، کوئری‌تون رو تایپ می‌کنه، و متن/کلاس/وضعیت
  visible و enabled هر گزینه‌ی نتیجه رو چاپ می‌کنه.
- **`python explore_hamrah_catalog.py`** — مسیر برند ← مدل تو کادر انتخاب
  خودروی همراه مکانیک رو برای چندتا برند اول تو یه مرورگر قابل‌مشاهده طی
  می‌کنه و هر مرحله رو چاپ می‌کنه. برای اضافه کردن ردیف جدید به
  `app/data/car_brand_mapping.json` مفیده.

هر چهارتا، صرف‌نظر از `.env`، `HEADLESS_BROWSER=false` رو اجبار می‌کنن تا
دقیقاً ببینید صفحه داره چیکار می‌کنه.

## ردیابی خطاهای اسکرپ/تخمین تو پنل مدیریت

هر آگهی‌ای که زمان‌بند روش کار می‌کنه، حتی اگه شکست بخوره، یه ردیف تو
دیتابیس ثبت می‌شه - پس هیچی برای همیشه دوباره‌وتلاش نمی‌شه. داشبورد این‌ها
رو نشون می‌ده:

- یه آمار **نرخ موفقیت** برای ۲۴ ساعت اخیر (تخمین‌های موفق ÷ آگهی‌های
  تلاش‌شده، بدون احتساب آگهی‌های اسقاطی که عمداً skip شدن).
- یه **جدول خطاها** که نشون می‌ده کدوم آگهی‌ها گیر کردن، تو کدوم مرحله
  (`دریافت اطلاعات دیوار` یا `تخمین قیمت`)، با متن خطا و لینک به آگهی.

این با دو ستون جدید روی `SeenListing` (`status`, `error_message`) پیاده
شده - به `app/db/models.py::ListingStatus` نگاه کنید. چون این پروژه از
ابزار migration (مثل Alembic) استفاده نمی‌کنه، اضافه‌شدن این ستون‌ها به یه
دیتابیس از قبل پر‌شده خودکار انجام نمی‌شه (`init_db()` فقط جدول‌های جا
افتاده رو می‌سازه، نه ستون‌های جا افتاده روی جدول موجود). اگه دارید یه
دیپلوی قبلی رو آپدیت می‌کنید و خطای دیتابیس درباره‌ی `status` یا
`error_message` دیدید، جدول `seen_listings` رو (یا کل دیتابیس رو، اگه
پروژه‌ی Neon تازه‌اید) پاک کنید تا خودش دوباره ساخته بشه.

## تنظیم/نگه‌داری سلکتورهای اسکرپینگ

دیوار `robots.txt` را طوری تنظیم کرده که دسترسی خودکار را غیرمجاز اعلام
می‌کند و ساختار HTML صفحاتش هم به‌مرور تغییر می‌کند؛ به همین دلیل دو فایل
زیر تمام سلکتورهای CSS را در یک دیکشنری بالای فایل نگه می‌دارند تا در صورت
نیاز فقط همان‌جا را ویرایش کنید، نه کل منطق را:

- `app/services/divar_client.py` → دیکشنری `SELECTORS`
- `app/services/price_estimator.py` → دیکشنری `SELECTORS` (این یکی از روی
  بازرسی مستقیم صفحه‌ی واقعی همراه مکانیک نوشته شده و آماده‌ی استفاده است.
  چون سایت با Next.js/CSS-Modules ساخته شده، اکثر سلکتورها به‌جای کلاس کامل
  از `[class*="..."]` روی بخش پایدارِ قبل از هش استفاده می‌کنند تا با هر
  بیلد جدید سایت خراب نشوند. یک محدودیت شناخته‌شده دارد: تشخیص خودکار اینکه
  کدام قطعه‌ی خودرو باید در تب «رنگ‌شدگی» در برابر «تعویض‌شدگی» تیک بخورد،
  فقط بر اساس چند کلمه‌کلیدی ساده است - جزئیات در docstring بالای همان فایل)

نحوه‌ی به‌روزرسانی یک سلکتور: صفحه‌ی موردنظر را در کروم باز کنید، روی عنصر
راست‌کلیک → Inspect، و یک سلکتور پایدار (id، `name`، `role`، یا پیشوند کلاس
قبل از هش) پیدا کنید.

همچنین به یاد داشته باشید نرخ درخواست (`REQUEST_DELAY_SECONDS`) را پایین
نگه دارید تا احتمال بلاک‌شدن IP کم شود؛ این یک ابزار شخصی برای رصد قیمت
است، نه یک خزنده‌ی تجاری.

## دستورات ادمین در تلگرام

```
/admin_users                       لیست همه‌ی کاربران
/admin_activate <telegram_id> <days>   فعال/تمدید اشتراک کاربر
/admin_disable <telegram_id>       غیرفعال کردن کاربر
/admin_enable <telegram_id>        فعال کردن دوباره‌ی کاربر
```

(همین کارها از پنل وب هم قابل انجام است.)

## افزودن درگاه پرداخت واقعی

معماری از اول برای این آماده شده:

1. یک کلاس تازه در `app/services/payment/` بسازید که از
   `PaymentProvider` (در `base.py`) ارث ببرد - مثلاً `ZarinpalPaymentProvider`.
2. در `app/services/payment/__init__.py`، شاخه‌ی جدید را به `get_payment_provider`
   اضافه کنید.
3. `PAYMENT_PROVIDER=zarinpal` را در `.env` تنظیم کنید.

هیچ‌کدام از بات، پنل وب یا مدل‌های دیتابیس نیازی به تغییر ندارند، چون همه
از طریق `activate_subscription` در `app/services/subscription.py` کار
می‌کنند.

## ساختار پوشه‌ها

```
app/
  config.py              تنظیمات (از متغیرهای محیطی خوانده می‌شود)
  db/                     مدل‌ها و session دیتابیس (SQLAlchemy)
  services/
    divar_client.py       اسکرپینگ دیوار (Playwright)
    price_estimator.py    اتوماسیون فرم همراه مکانیک (Playwright)
    deal_checker.py        منطق مقایسه‌ی قیمت
    notifier.py            ساخت و ارسال پیام تلگرام
    subscription.py         منطق اشتراک/کاربر
    payment/                رابط قابل‌توسعه‌ی پرداخت
  bot/                    ربات تلگرام (aiogram) - هندلرها و کیبوردها
  web/                    پنل مدیریت (Flask) - روت‌ها و قالب‌ها
  scheduler/              زمان‌بند اسکن دوره‌ای (APScheduler)
  constants/cities.py     نگاشت شهرها به اسلاگ دیوار
main.py                  نقطه‌ی ورود - همه چیز را با هم اجرا می‌کند
```

## محدودیت‌های شناخته‌شده (برای گزارش پروژه دانشگاهی هم مفید است)

- دیوار API عمومی برای خواندن آگهی‌ها ندارد؛ این پروژه از اسکرپینگ صفحات
  عمومی استفاده می‌کند که در تضاد با `robots.txt` دیوار است. برای استفاده‌ی
  شخصی و با نرخ درخواست پایین طراحی شده، نه برای مقیاس تجاری.
- سلکتورهای صفحه‌ی همراه مکانیک از روی بازرسی مستقیم صفحه‌ی واقعی نوشته
  شدن و آماده‌ی استفاده‌ان. تنها محدودیت شناخته‌شده: تشخیص اینکه کدام قطعه‌ی
  بدنه باید در تب «رنگ‌شدگی» در برابر «تعویض‌شدگی» تیک بخورد، فقط با چند
  کلمه‌کلیدی ساده انجام می‌شود (`KNOWN_BODY_PARTS` در همان فایل) و ممکنه
  برای عبارت‌های پیچیده‌تر دیوار دقیق نباشه.
- تشخیص برند/مدل از روی متن آگهی دیوار به‌صورت best-effort انجام می‌شود
  (`app/services/deal_checker.py::_split_brand_model`) و ممکن است برای
  برخی خودروها نیاز به بهبود داشته باشد.
- دیتابیس SQLite برای یک استقرار کوچک مناسب است؛ برای مقیاس بزرگ‌تر به
  Postgres مهاجرت کنید (فقط تغییر `DATABASE_URL`).
